# Daily Agent Operating Guide

Read this file at the **start of every run.** You are an automated assistant that makes one
small, real improvement to the Nocturne iOS app per run. Your job is to leave the repo a little
better — never worse. The rules below are non-negotiable; they exist because a previous loop
broke `main` repeatedly by ignoring them.

## Hard workflow rules

1. **Never push to `main`.** `main` is branch-protected: direct pushes are rejected and a PR
   cannot merge until CI is green. Always: branch off `main` → commit → open a PR → stop. A human
   reviews and merges.
2. **One small, focused change per run.** A single screen, one helper + its use, one test file,
   one doc fix. If a change feels large, do the smallest valuable slice and note the rest.
3. **Self-check before you commit.** If the tooling is available in your environment, run
   `swiftlint --strict` and fix every violation before committing. (The full build/test gate runs
   in CI on your PR regardless — see "How CI gates you".)
4. **Conventional commits, single author.** Use `feat:`/`fix:`/`chore:`/`docs:`/`test:` prefixes.
   **Never** add `Co-Authored-By`, "Generated by", or any assistant/footer trailer to commits or
   PR descriptions. History must read as the repo owner's own work.
5. **Keep `docs/HANDOFF.md` current** in the same PR — update STATUS / the "Next up" list to
   reflect what you did.

## What to work on (in priority order)

Pick the **first** applicable item; don't invent work:

1. The top unchecked item in `docs/HANDOFF.md` → **Next up**.
2. A `// TODO:` or `// FIXME:` in the codebase you can resolve cleanly (grep for them).
3. A genuinely missing **test** for an existing, untested type (improves coverage of real code).
4. A small, real **UX / accessibility / polish** improvement to an existing screen.
5. A **documentation** fix (stale README/HANDOFF, missing doc-comment on a public type).

## The rule that matters most: no orphaned code

**Every new symbol you add must be used by the app in the same PR.** If you write a helper,
extension, model, or service, it must be wired into a real screen / call site in that same PR.
If you can't find a real use for it, **don't add it** — an unused file is not an improvement, it's
debt. (Past loops failed precisely here: they added `Color+Extensions`, `Numeric+Extensions`,
`NetworkError`, etc. that nothing referenced, and they were all deleted.)

Before adding any new file, grep the repo: does this capability already exist? (`Color(hex:)` is
in `Theme.swift`; duration/Date formatting is in `Duration+Formatting.swift` / `StatsModels.swift`;
haptics in `HapticManager.swift`. Reuse, don't duplicate.)

## Project conventions you must follow

- The Xcode project is generated by **XcodeGen** from `project.yml` and is git-ignored. After
  adding/removing files run `xcodegen generate`. Never commit `SpotiStats.xcodeproj`.
- Secrets are git-ignored. If your environment lacks `SpotiStats/Resources/Secrets.xcconfig`,
  create it from the example: `cp SpotiStats/Resources/Secrets.xcconfig.example
  SpotiStats/Resources/Secrets.xcconfig` (placeholder values build fine; tests use mocks).
- Lint is strict: avoid force-unwraps (`!`) and `try!`; keep lines ≤ 120 chars; standard 4-space
  indentation. CI runs `swiftlint --strict` and fails on any warning.
- Backend (Supabase Edge Functions, Deno) is in `supabase/functions/`; its tests run via
  `deno test`. Don't touch backend unless the task is explicitly backend work.
- Architecture / state / decisions live in `docs/HANDOFF.md` — it is the source of truth.

## How CI gates you (your safety net)

Your PR triggers GitHub Actions: a macOS job runs `swiftlint --strict` + the full XCTest suite,
and a Linux job runs the Deno tests. `main` is branch-protected to require both. So even if your
local environment can't build the iOS app (no Xcode), opening a PR is safe: a broken change simply
fails CI and waits for a human — it can never reach `main`. Prefer to self-check first anyway, to
avoid wasting CI runs and to keep PRs clean.

## Definition of done for a run

- A branch with one focused, conventional commit (or a few atomic commits), pushed.
- A PR opened into `main` with a clear title + body explaining the change and how it was verified.
- `docs/HANDOFF.md` updated.
- No unused new symbols. No `main` push. No co-author trailers.
